# Tailscale sidecar configuration

`serve.json` is generated by `just up tailscale` and applied by `containerboot` through
`TS_SERVE_CONFIG`. It is generated rather than committed because it names the relay's
address on a subnet chosen at deploy time. It must stay plain JSON with no extra keys —
Tailscale parses it into its own `ipn.ServeConfig` type, so anything it does not
recognise is a liability rather than a comment. `${TS_CERT_DOMAIN}` is substituted by
containerboot with this node's MagicDNS name.

## Prerequisites on the tailnet

MagicDNS and HTTPS Certificates must both be enabled under
[admin → DNS](https://login.tailscale.com/admin/dns) before Tailscale will issue the
certificate this configuration terminates with. `just up tailscale` verifies it by
reading `CertDomains` from `tailscale status --json`, which stays empty until both are
on, and stops with instructions rather than letting TLS fail later and opaquely.

Enabling HTTPS publishes the node's name on a public certificate-transparency ledger.
The node stays unreachable outside the tailnet; only its existence is disclosed.

## Why TLS-terminated TCP rather than an HTTP proxy

Tailscale Serve can act as an HTTPS reverse proxy (`Web` handlers with `Proxy`), which
would give the relay `X-Forwarded-For` and `X-Forwarded-Proto`. We deliberately do not
use it.

The relay is almost entirely WebSockets, and Serve's HTTP proxy path has a history of
upgrade regressions and is known to strip query parameters from upgrade requests.
Terminating TLS and forwarding raw TCP sidesteps that whole class of problem: after
termination it is a byte stream, and the relay speaks HTTP and WebSocket over it
exactly as it would over a direct connection.

Tailscale still issues and renews a real certificate for the MagicDNS name, which is
what makes the Android client's certificate validation work without any trust-store
fiddling.

## Why not a shared network namespace

`network_mode: service:tailscale` is the more common recipe and is simpler to write.
It is not used here because it makes the relay's networking hostage to the sidecar:
when the sidecar restarts it gets a *new* network namespace, and the relay is left
orphaned on a dead one — still passing its own health check on its own loopback, while
unreachable from anywhere. A crash restart is not orchestrated by Compose, so
`depends_on` cannot rescue it.

Instead the two containers are independent, on a small dedicated bridge network with
fixed addresses. The sidecar can be recreated, updated or crash-looped without the
relay noticing.

## The trade-off this makes

A raw TCP forward preserves no client address, so the relay sees every tailnet
connection as coming from the sidecar. Two consequences:

- **Per-source rate limits collapse into a single bucket.** The limits that matter on a
  tailnet — `ratelimit.requests_per_minute_per_principal` and the per-subscriber input
  limits, both keyed by the authenticated token — are unaffected.
- **Transport security is established by address, not by header.** There is no
  forwarded-protocol header on a TCP forward, so `just up tailscale` sets
  `security.tls_terminated_by_networks` to this deployment's dedicated subnet:
  connections from it are known to have arrived through the Tailscale TLS terminator.
  The development loopback exemption (`security.allow_insecure_loopback`) stays off.

That subnet is sized `/29` and contains nothing but the relay and the sidecar. The
relay's API is deliberately not published to the host either, so nothing else on this
machine can inherit that trust over plain HTTP.

## Reaching the admin API

Because of the above, admin requests from the host would arrive over a different
network and be refused. `just admin`, `just metrics` and `just flush` run their request
from inside the sidecar instead. `just settings`, `just set` and `just status` are
unaffected: the first two talk to the database directly, and the health listener is
published and enforces no transport requirement.
